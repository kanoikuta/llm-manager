> `model_manager.py` L988-1001（PDH 共享显存的三个坑）、`ui.html` L204-211（阈值取值理由）、

## 一、数据流

```
GpuMonitor 线程（每 1 秒采一次）
   └─ nvidia-smi + pdh.dll(共享显存) ──> deque(maxlen=480)   ← 缓存
                                            │
页面 tick（每 1.5 秒轮询）──────────────────┘   页面读缓存，不重复起 nvidia-smi
```

- **采样 1 点/秒、存 480 点** = 8 分钟窗口。已经比画布像素还密（320 px 上 0.67 px/点），
  再加点只等于拉长窗口，画面不会更细。
  > 节奏换过两次（3 秒/80 点 → 1 秒/200 点 → **1 秒/480 点**，都是用户要求的）。
  > 成本：`nvidia-smi` 单次 ~49 ms → 1 秒一次约占一个核的 5%（这台 16 线程无所谓）；
  > 每次轮询的 JSON 大了约一倍（~11 KB），手机上无感。想再密得换 NVML
  > （nvidia-smi 的开销大半是每次起进程）。
- 每次采六个字段（和只采一个一样快）：
  `power.draw, utilization.gpu, temperature.gpu, memory.used, memory.total, power.limit`
- `temp_max` / `power_max` 是**累计峰值**，**不在 `latest` 里**（`latest` 只放最近一次采样），
  由 `snapshot()` 单独塞进返回值。口径 = 管理器本次启动以来，重启清零。

## 二、常量在哪里、动它会影响什么

| 常量（`ui.html` 顶部） | 控制什么 | 当前值 | 满载实测 |
|---|---|---|---|
| `TEMP_WARN_C` | 温度**数字**标红（曲线颜色不受它管） | 50 | 51~60 |
| `POWER_WARN_W` | 功耗数字标红 | 350 | 366 |
| `MEM_WARN_GB` | 内存数字标红 | 32 | — |
| `TEMP_MAX_C` | 温度曲线 **y 轴上限**（决定曲线高度 + 渐变取色） | 100 | — |
| `POWER_MAX_W` | 功耗曲线 y 轴上限 | 517.5（实测功耗墙） | 366 |

**两个标红阈值都故意设在满载值之下**（50<51、350<366），所以满载时两个「最高 xx」都会变色。
**改之前先想清楚要哪种行为**：设在满载之下 = 满载变色；设在之上 = 只有真异常才变色
（2026-09-13 温度原来挂 70、永远够不着，用户指出后统一）。
**温度曲线永远到不了纯红**：y 轴上限 100 而满载才 51~60，只爬到半格、显示成黄绿。

## 三、共享 GPU 内存（`SHARED_VRAM`）

任务管理器 GPU 页那个值，**nvidia-smi 不报**。显存吃紧时驱动把数据挪到系统内存，
平时 ≈0.4 GB，涨起来说明快溢出了。走 ctypes 调 `pdh.dll` 读
`\GPU Adapter Memory(*)\Shared Usage`（和任务管理器同源）。

- **三个 ABI 坑全部写在 `model_manager.py` L988-1001**，动这段代码前必读（写错直接 SIGSEGV）。
- 这组计数器**每块 GPU 一个实例**（独显、核显、基本显示适配器会各算一个），
  挑法是**看谁的「专用显存占用」最大**（核显是 0），不用去翻 LUID。
- 整段用 `try/except` 包死：读不到返回 `None`、页面显示 `—`，**绝不允许它把监控线程搞崩**。

## 四、输出速度记录（`Runtime.perf`）

`note_tps()` 每次推理完记一条，`deque(maxlen=50)`，**跨模型不清零**：

| 字段 | 来自 llama.cpp 的 `timings` | 说明 |
|---|---|---|
| `tps` | `predicted_per_second` | 平均解码速度 |
| `accept` | `draft_n_accepted / draft_n` | MTP 命中率；`draft_n` 为 0 时是 `None`（页面显示「无投机」） |
| `n` | `predicted_n` | 这次生成了几个 token |
| **`pin`** | **`prompt_n + cache_n`** | **输入 token 总数**（v0.3.05 加） |
| **`ms`** | **`predicted_ms`** | **输出总耗时（毫秒）**（v0.3.05 加） |
| `at` / `model` | — | 服务端 `strftime` 存字符串，省得手机上算时区 |

- **`n`（predicted_n）必须记**：首 token 有固定开销，只吐 8 个 token 的短回复平均下来显示
  **6 t/s**，同模型长回复是 **108 t/s**。不标 token 数，历史里的洼地会被误读成掉速。
- **`pin` 必须把 `cache_n` 加上**：只取 `prompt_n` 的话，连续对话里命中前缀缓存的那一大截
  会凭空消失，显示出来的「输入」远小于实际上下文。两个字段名 2026-09-21 拿本机 8092 的
  真实响应核对过（`prompt_n=25 / cache_n=0 / predicted_ms=436.606`，40 tok 出 0.44s，
  和 `n/tps` 交叉验算对得上）。
- **`ms` 用 `predicted_ms`，别拿 `n/tps` 反推**：反推出来的是纯解码时间，
  `predicted_ms` 是 llama.cpp 自己记的整段生成墙钟。
- **页面侧必须判 null**：v0.3.05 之前写的记录没有 `pin` / `ms`，
  `drawPerf()` 里那几段都先判 `!= null` 再拼，否则会显示「入 undefined / 用时 NaNs」——
  升级后手机上会新旧记录混在一屏。
- 页面侧（`ui.html` 的 `drawPerf` / `drawTps`）两条约束写在 `openPerf()` 上面的代码注释里，
  其中「只在条数变了时重建 DOM + 存取 `scrollTop`」别破坏 —— 否则 1.5 秒轮询会把滚动弹回顶部。
- **入口在「更多 → 记录」**（v0.3.04 起，`#perf` 是「更多」的第二层，`z-index:25`）。
  以前是状态卡统计条里那个「记录 ›」格子，统计条 2026-09-21 被用户删了。
  `render()` 里的 `drawPerf(false)` **要留着** —— 记录弹层开着时得跟着轮询刷新，
  它自己在 `display:none` 时早退。

## 五、排查

| 现象 | 原因 |
|---|---|
| 共享显存显示 `—` | PDH 读失败（已吞异常）。查 `logs\manager.log`，或先单独跑探针验 ABI |
| 曲线断一截 / 有点是空的 | 采样线程被 nvidia-smi 卡住（单次 ~49 ms）。确认没有别的进程在狂跑 nvidia-smi |
| 「最高 xx」不涨 | 它只在**本次启动**内累计，重启管理器就清零，这是设计 |
| 温度数字一直灰 | `TEMP_WARN_C` 设得比满载还高 —— 见第二节的取舍说明 |
