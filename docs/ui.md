# ui.html（网页界面）

纯 HTML+CSS+JS，无框架无依赖，约 1570 行。**改它不用重启管理器**（Python 按 mtime 读文件），
刷新页面即生效，模型纹丝不动。

## 〇、版面结构（2026-09-26 更新，v0.3.26）

风格参考一张极简 UI 草图（分段控件、细线图标、大留白、轻字重），

颜色只留给状态点和四条曲线，界面本身是灰度的。**改配色时别把蓝色加回变量里。**

**圆角：三级 + 药丸**（v0.2.13 起，用户 2026-09-20 放开了原来「统一一个 `--r`」那条限制）。
`--r-lg:22px` 外层容器 / `--r:16px` 控件 / `--r-sm:11px` 卡片内部小块 / `--r-pill:999px` 分段槽。
`--well` 是 `--r-sm` 的别名，老代码引了几十处，别删。**要加新圆角先复用这四档，别随手写 px。**

**顶上没有标题栏**（v0.3.05）：原来那行「模型管理器 + 版本号小胶囊」挪到「更多」最底下
当落款（`.about` 那个 div）。`#ver` 的 id 没变，脚本末尾 `$('#ver').textContent` 那行不用改。
⚠ 跟着要改的是 `.sub`（出错时才冒出来的那行黄字）的 `margin-top`：**`-8px` → `0`** ——
那个负值本来是抵掉标题的 `padding-bottom` 的，标题没了会把黄字顶出安全区。

主屏按手机操作顺序组织：监控在上，模型状态卡和五个操作按钮固定在屏幕底部，模型卡在按钮上方。

### ⚠ 三个容易踩的点

1. **图标颜色**：必须有 `svg{fill:currentColor}` 这条全局规则。内联 `<symbol>` 里的形状
   没有 `fill` 属性 → 默认是**黑色**，在深色按钮上就是一团看不见的黑。
   v0.2.7 用户报的「按钮里是黑色看不清」就是这个。
   `stroke` 型的图标自己写了 `fill="none"`，那是表现属性，**优先级高于继承值**，不会被覆盖。
2. **`.acts>button` 必须排在 `button.gray` 之后**：同优先级下后者胜。
3. **别造重复 id**：状态卡是 `innerHTML` 每次重建的，里面那颗卸载按钮叫 `btnUnload`；
   「更多」弹层里那颗静态的必须叫别的名字（现用 `btnUnloadSheet`），
   否则全文档两个同名 id，`$('#btnUnload')` 只会拿到先出现的那个，另一颗永远点不动。

### ⛔ 绝对不要用原生 confirm() / 它会让按钮「点了没反应」

**2026-09-20 事故**：用户报「睡眠 / 关机 / 卸载 全都没反应」。排查结果 ——
这些按钮的 onclick **都绑上了、也没被别的元素挡住**（`elementFromPoint` 全是 HIT、
控制台没有任何报错），问题出在它们**恰好是仅有的几个走原生 `confirm()` 的按钮**：
手机浏览器（Safari、微信、各家 WebView）会「阻止此页面创建更多对话框」，
之后 `confirm()` **不弹框、直接返回 false** → 函数第一行就 `return` → 表现就是按钮死了。

**受害按钮清单（改按钮时对着查）**：睡眠、完全关机、卸载（状态卡那颗 + 「更多」里那颗）、
接管。共同点只有一个：调 `confirm()`。

**规矩**：确认一律走页面自己的 `ask(title, body, okLabel, danger)`（返回 `Promise<boolean>`，
弹的是 `#ask` 那层）。**`alert()` 目前还在用**（只在报错路径），暂时没出问题；
哪天用户说「报错也看不到」，就把它一起换成页面内的提示条。

两个使用要点：
- 调用方必须 `await ask(...)` 再往下走；
- **外面点按钮时不要 `await` 那个 onclick** —— 它会一直挂到用户点确定为止
  （假 DOM 测试里踩过，整条测试直接卡死）。

`dom_power_test.js` 里加了一条静态闸门：把注释剥掉后全文搜 `confirm(`，
出现就 FAIL。同时沙箱里 `confirm` 显式设成 `undefined` —— 还有漏网的会直接 TypeError。

### 末段「不同配置下的 t/s」怎么排（v0.3.28 → v0.3.29 搬到 Python）

**这段文本已不在 `ui.html` 里算了** —— 2026-09-26 用户要求「记录最好是程序自动写出结果，

用户在意的正是「数是谁写出来的」，而且页面里算的东西 AI 读不到（文件能读）。

排版规矩的**为什么**写在 `build_tps_summary()` 上面那段注释里（改之前先读），
这里只记用户的原话和几条不许改坏的东西：

用户 2026-09-26 的要求：**不写逐次流水**（那是「记录」弹层的活，条数一长没法看）；同一设置先取
**平均**当参考；同一族里**每条都一样**的字段不重复写 ——
「同样设置只有 MTP 区别，只写 `MTP3 90t/s MTP4 92t/s`」；
「详细平均速度只写在日志里作为 ai 看的，避免反复测速」。

- 分组三级：**模型 → 上下文 · KV → MTP 变体**。模型必须先分 —— 跨模型比 t/s 没有意义。
- 变体标签只写**有区别**的那一档：只有 nmax 在变 → `MTP 3` / `MTP 4`；
  p-min 也在变 → `MTP p-min 0.7`（**别缩成 `MTP 0.7`**，那读起来像 nmax）；
  只有一条记录、或两样都在变 → 写全 `MTP 3/0`。
- **次数一定要括注**（`（2 次）`）：只跑过 1 次的「平均」是噪声，而用户是拿它做取舍的。
- 老记录（v0.3.05 之前，没有 `ctx` / `kv` / `mtp` 字段）写「配置未记录 / MTP 未记录」，
  **不许**印成「无 MTP」—— 那是在替一条根本没存过这个信息的记录断言一件事。
  明确的 `mtp:'none'` 才写「无 MTP」。
- 配置串**只走 `recCfg()` 一份**（记录弹层和末段共用）：同一批数据在两处显示得不一样时，
  看的人第一反应是「哪边坏了」。
- 顺序：模型按最近一次推理**倒序**（刚用过的在最上面）；变体按 nmax、p-min **升序**
  （跟用户给的例子一致；按速度排会让人以为位置有含义）。
- 这一段**不跟着 `tick()` 重建**（和整个日志弹层一样，打开时才填），数据源是
  `lastState.perf`，和 `drawPerf()` 同一份 —— 别为它单开接口（那要改 `model_manager.py`，
  而 `ui.html` 是免重启生效的，别把这个便利丢掉）。

> ⚠ **`lockZoom()` 没法在无头 Chrome 里端到端验**：`element.focus()` 在无头里

## 一、两个不能破坏的机制

1. **版本号只在第一行** `<!-- UI_VER: 0.3.x -->`。Python 发页面时把 HTML 里的 `__UI_VER__`
   占位符替换成这个值。页面拿服务端返回的版本跟自己内置的比，不一致就自动重载。
   手写两份 → 永远对不上 → **手机无限刷新**（踩过；现在页面还有 15 秒防抖兜底，最多刷一次）。
2. **轮询 `tick()` 每 1.5 秒一次**，读的是服务端缓存（`GpuMonitor` 自己 1 秒采样一次），
   所以轮询不重复起 `nvidia-smi`。任何"每次 tick 都重建 DOM"的写法都要警惕。

## 二、画图

`drawLine(id, hist, limit, color, ramp)` —— y 轴固定 0 到 `limit`，**曲线高度 = 占用率**。

- `ramp` 给了就是**热力曲线**（内存/功耗/温度）：颜色只由 y 轴高度决定，底=本色、顶=纯红。
  实现 = **把一条竖直渐变直接当 `strokeStyle`**，canvas 按每个像素的 y 取色，
  折线 / 填充 / 末端圆点自动全对，不用逐段算插值。`ramp` 不给就是单色（显存故意不渐变）。
- **两个坑写在 `ui.html` L360 附近的注释里**（色标要插中间一档，否则绿色会从发灰的橄榄色穿过；
  填充色相要跟折线一起渐变），改渐变前必读。
- `drawTps` 的 y 轴**按数据最大值动态缩放**（t/s 没有天然上限，换模型就全变）——
  这和上面四条固定 y 轴的曲线不一样。
- **`drawTps` 只吃数字数组，不吃记录对象**。2026-09-20 修掉一个从加这个图那天就在的 bug：
  `drawPerf()` 原来传的是 `rows.slice().reverse()`（整条记录对象），而 `drawTps` 里
  `v > 0` 对对象恒为 false → 全被过滤掉 → **有记录也永远显示「至少要有两次记录才画得出曲线」**。
  现在是 `.map(r => r.tps)`。同类坑：给这种"只处理数字"的函数传对象数组，
  **不会报错**，只是静默变成空数组 —— 改这里时先确认过滤后还剩几条。

## 三、列表 / 弹层：滚动位置必须保住

列表类 UI（模型列表、速度记录）统一遵守：

- **只在「数据条数变了」时重建 DOM**，其余时候只更新数值。靠一个 `sig` 字符串比对。
- **重建前后保存 / 恢复 `scrollTop`**：`const st = list.scrollTop` → 重建 → `list.scrollTop = st`。
  不做的话 1.5 秒轮询会把正在滚动的列表**弹回顶部**（模型列表先踩过，速度记录跟着踩）。

推理记录追加保存到 `logs/inference-history.jsonl`，管理器重启后恢复最近 50 条，历史文件保留完整记录；记录包含当时上下文、KV、MTP 深度/min、接受率和 tok/s。速度记录做成**弹层**而不是摊在页面上（条数会长，10 条就吃掉手机半屏；摊在页面上还得跟着
轮询重建）。理由写在 `openPerf()` 上面那段注释。**v0.3.05 起入口是操作槽里那颗「记录」**
（`#btnPerf`，在「更多」左边），不是弹层里的按钮。

`drawPerf()` 那条小字（命中 / 入 / 出 / 用时）**每一段都要先判 `!= null` 再拼** ——
`pin` / `ms` 是 v0.3.05 才有的字段，服务端的 `perf` 要重启才清零，
所以升级后手机上一屏里会新旧记录混着，不判就显示「入 undefined / 用时 NaNs」。
`#perfList .it .l em` 单独放开了 `white-space` —— `.plist` 那套是 nowrap + ellipsis，
四段挤不下时最后一段会被**无声截掉**。

## 卸载状态保护

Windows 对高权限 llama-server 返回 Access denied 时，管理器会通过 8092 监听 PID 辅助识别；卸载命令成功后立即进入显存回落等待，不再重复轮询进程；命令失败时快速核对监听 PID，页面保留错误状态并提示显存可能仍被占用。


## 五、重载时的进程保护

模型配置通过当前控制台入口（80 或兼容入口 8091）的 `/api/config` 保存。引擎本身监听 8092；重载时管理器负责先停止它，再用新参数启动。Windows 若拒绝停止旧 PID，必须保留错误状态并取消新启动，不能继续 `ensure()`，否则会留下两个 `llama-server` 占用同一张卡。`taskkill` 返回「拒绝访问」表示当前管理器令牌不能终止该 PID（常见于不同权限级别/账户启动）；这是进程权限问题，不是 8091/8092 的网络访问错误。


## 六、重启管理器（v0.3.31 加）

「更多」里那颗按钮。**它跟睡眠/关机不是一类**：那两个把机器弄下线、不会自己回来，这个
只断几秒就回来 —— 所以前端**不能**套 `enterShutting()`（它会 `stopTick()`，而且没有任何
回滚路径，套上去页面就永远停在「正在重启」）。重启走自己的探测循环。

### 服务端（`model_manager.py`）

- `POST /api/restart`
- **闸门**：`RT.phase` 是 `loading`/`stopping`、或 `engine_generating()` 为真
  （问 8092 的 `/slots` 有没有 `is_processing`）时返回 **409**，前端只弹框不动状态。
  点这颗按钮的意图通常是「让新配置生效」，不是「砍掉我正在等的回复」。
  睡眠/关机**不设**这道闸门，因为那两个本来就是「我要断服务」。
  `engine_generating()` 问不到就当没在忙 —— 引擎没加载或卡死时本来就该允许重启。
- `spawn_restart()` 生成一个 `.vbs` 丢给 `wscript`。**为什么绕这一道**：wscript 那句
  `sh.Run(cmd, 0, False)` 第三个参数 False = **不等它结束**，新进程也不继承本进程的控制台，
  本进程一退它照样活着。直接 `subprocess.Popen` 的话子进程跟着父进程一起走，重启就变成自杀。
- **新进程必须带 `--restart-wait <端口>`**：它启动时先等那个端口空出来再往下走。不带的话
  它会撞上还没退干净的自己，在 `main()` 里看到「端口已被占用」直接退出 ——
  手机上看起来就是「点了重启，然后再也没起来」。
- **端口要原样带过去**（`--console-port` / `--proxy-port` / `--engine-port`）。只带
  `--restart-wait` 的话，用 `--console-port 8080` 起的管理器重启后会**跳回 80**。
  v0.3.31 第一版就是这个 bug，写 e2e 测试时才暴露出来。
- `exit_soon()` 延迟 1.5 秒再 `os._exit(0)`：**先把 HTTP 响应发出去**，否则手机上只看到
  「请求失败」。用 `os._exit` 是故意的 —— 跳过解释器收尾，且**不做任何清理**：引擎要留着
  给新实例的 `adopt_existing()` 认领，不然重启就变成「卸载又重载」，白多花十几秒。

### 前端（`ui.html`）

`#btnRestart` → `ask()` 确认 → POST → 成功就 `stopTick()` + 状态卡改成「正在重启管理器…」，
然后每秒探一次 `/api/state`：

- 探通了 → `location.reload()`（**重载是为了拿新的 `UI_VER`**，重启往往正是因为换了新代码）
- 探到 **401** → **也重载**：服务其实已经回来了，只是 key 变了（多半刚改过 `config.json`
  的 `api_key`），别在这儿干等 45 秒
- 45 次还没通 → 不再装死，`startTick(); tick()` 把轮询交回去，状态卡改口说连不上
